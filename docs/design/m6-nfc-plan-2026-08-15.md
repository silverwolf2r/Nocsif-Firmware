# M6 — NFC (ST25R3916) · risk-first phased plan

*Decided 2026-08-15. Milestone after reliability hardening; precedes M5 WiFi.*
*Device class: HF NFC reader/writer + card emulation for **authorized security testing**.
Wording throughout is device-class neutral (see §Wording).*

---

## 0. Objective & constraints

Bring up the ST25R3916 13.56 MHz HF front-end and deliver, phase by phase, tag read →
read/write → card emulation + NDEF → key recovery + saved-cards + extended parsers, wiring
each real behavior into the **already-registered** `build_nfc()` rows (`nfc.read / .write /
.emulate / .saved / .keyrec / .ndef`). **Fill, don't rebuild.**

Decisions taken 2026-08-15:
- **Driver foundation = port ST's RFAL** (RF Abstraction Layer) to ESP-IDF. *Superseded the initial
  "native minimal" pick the same day* after mining LilyGoLib showed **RFAL is the board-proven path**
  (`RfalRfST25R3916Class`/`RfalNfcClass`, `rfalNfcInitialize/Discover/Worker`) and the full-featured
  scope needs exactly RFAL's complete stack (T1–T4T, NfcV, ISO-DEP, listen-mode card emulation, NDEF)
  — painful to hand-roll. **Base = `wilson-elechouse/ST25R3916`** (self-contained: bundles the RFAL
  core `NFC-RFAL/` + the ST25R3916 driver `ST25R3916_ELECHOUSE/`, ESP32-S3-validated). We keep the
  public-domain **CRYPTO1 lib (crapto1)** only for P4 **offline key recovery (mfkey)** — RFAL does
  not do key recovery.
- **Scope = full-featured push** — P3 targets full T2T/NDEF card emulation (RFAL listen-mode); P4
  includes the extended parsers (EMV / DESFire / iCLASS·PicoPass) from the start. P3 listen-mode is
  still de-risked prototype-first (UID-only → T2T → NDEF).

### Foundation: the RFAL port (what P1 actually builds)
The vendored base splits into a **platform-agnostic core** (compiles ~as-is as a C++ ESP-IDF
component) and a **thin Arduino glue** (the port surface — rewrite for ESP-IDF):
- **Core, compile as-is** — `NFC-RFAL/src/` (48 files: `rfal_nfc/nfca/nfcb/nfcf/nfcv`, `rfal_isoDep`,
  `rfal_nfcDep`, `rfal_st25tb/st25xv`, `ndef_*` T2T–T5T, `rfal_config.h`, `st_errno`) + the
  chip/RFAL binding `ST25R3916_ELECHOUSE/src/{st25r3916.cpp, rfal_rfst25r3916*.cpp, rfal_mf1.cpp,
  *_iso15693*, *_crc, *_analogConfig, st25r3916_aat}`.
- **Port surface (rewrite for ESP-IDF)** — `st25r3916_com.cpp` (SPI transceive: Arduino `SPI` →
  esp-idf `spi_device_transmit` on **SPI3, 2nd device sharing SD**), `st25r3916_timer.cpp` (→
  `esp_timer`/FreeRTOS ticks), `st25r3916_interrupt.cpp` (→ `gpio_isr` on **GPIO5** → worker
  notify), and the pin-bound class constructor/`begin` in `st25r3916.cpp`/`rfal_rfst25r3916.cpp`.
- **Hardest integration point** — RFAL holds **CS asserted across multi-transfer sequences**, and
  the bus is shared with SD. Port CS via manual GPIO4 + `spi_device_acquire_bus()` (or hold the SD
  lock) around a full RFAL transaction so an SD access can't interleave. This is the #1 P1 risk.
- Vendored (gitignored) at `vendor/ST25R3916-elechouse/` via
  `git clone --depth 1 https://github.com/wilson-elechouse/ST25R3916.git`. To **build**, the needed
  sources move into a tracked `firmware/components/rfal/` (RFAL is BSD-3; keep ST/elechouse license
  headers).

## 1. Hardware ground truth (HARDWARE.md + verified in-code 2026-08-15)

| Fact | Value | Source |
|---|---|---|
| Chip | ST25R3916, **13.56 MHz HF only** (no 125 kHz LF) | HARDWARE.md §NFC |
| SPI CS | GPIO4 | HARDWARE.md |
| IRQ | GPIO5 (active-high) | HARDWARE.md |
| Bus | **SPI3_HOST**, shared MOSI34 / MISO33 / SCK35 (SD + NFC + LoRa) | `sdcard.c` |
| Power rail | **DLDO1** (AXP2101 `0x90` bit7 enable, voltage reg `0x99`) | HARDWARE.md + `power.c` |
| Card presence | **none** — no capacitive sense; reader must be field-on + polling to detect | HARDWARE.md |

**Bus coexistence (key):** `sdcard.c` already `spi_bus_initialize`s SPI3_HOST and *parks NFC-CS(4)
and LoRa-CS(36) high*. NFC therefore attaches as a **second `spi_bus_add_device` on the live bus**
(SD = slot 1, NFC = slot 2, LoRa = slot 3 — fits the 3 hardware CS lines). The ESP-IDF SPI-master
driver arbitrates concurrent SD↔NFC transactions; multi-transaction NFC sequences additionally take
`nocsif_sdcard_lock()` so an SD access can't interleave mid-anticollision. If SD is absent the bus
may be un-initialized → NFC init must `spi_bus_initialize` defensively (tolerate `INVALID_STATE`),
mirroring `sdcard.c`.

## 2. Integration rules (baked into every phase)

- **Safe-mode gate** — NFC bring-up is skipped when `nocsif_reliability_safe_mode()` is true
  (boot-loop guard). Init is **lazy** (first NFC-screen entry / first arm), not at boot, to keep
  boot fast and isolate risk.
- **LVGL single-threaded** — IRQ(5)→ISR→**`nfc_task` worker**. UI callbacks only *signal* the
  worker (command queue); the worker does all SPI I/O and posts results back via the live-label /
  `lv_async_call` path. Same shape as `ducky.c` / `usb_gadget.c`. Long CRYPTO1 recovery runs
  chunked at low priority — never on the LVGL task.
- **Rail** — add `nocsif_power_nfc_rail(bool)` to `power.c` following the exact `nocsif_power_sd_rail`
  precedent (set DLDO1 voltage `0x99`→3.3V, then enable `0x90` bit7). Confirm the DLDO1 enable bit
  against XPowersLib at bring-up (variants differ; some map DLDO1=`0x90` b7, DLDO2=`0x91` b0).
- **New files** — a tracked `firmware/components/rfal/` (RFAL core + ST25R3916 driver + the ESP-IDF
  platform glue, compiled as C++) + a thin `firmware/src/nfc.{c,h}` wrapper (worker + UI glue) added
  to `CMakeLists.txt` SRCS. `crapto1` (P4 key recovery only) added later. `esp_partition`/`nvs_flash`
  already in PRIV_REQUIRES; `nfc.c` REQUIRES the `rfal` component.
- **Storage** — dumps / traces / saved-cards buffered to `/sd/nfc/…` under the SD lock, not RAM;
  large working tables to PSRAM.
- **Per phase** — one branch → PR → squash-merge, **verified on-device**; build from PowerShell
  `-j 2`, flash `--no-stub` app-only (preserves NVS).

## 3. Phases

### P1 — RFAL platform port + read UID · **MEDIUM · foundational** (raised from LOW — now includes the ESP-IDF port)
The "prove the silicon" phase — stand RFAL up on ESP-IDF; every later phase reuses it.
- Move the RFAL core + ST25R3916 driver into a tracked `firmware/components/rfal/` (C++ component);
  add `nocsif_power_nfc_rail(bool)` (DLDO1 `0x99`/`0x90` b7, 3.3 V, `sd_rail` precedent).
- **Port the glue** (§Foundation): `st25r3916_com` SPI transceive → esp-idf `spi_device` on SPI3 as a
  2nd device (CS=GPIO4 manual + `spi_device_acquire_bus()`/SD-lock around each RFAL transaction);
  `st25r3916_timer` → `esp_timer`; `st25r3916_interrupt` → `gpio_isr`(GPIO5) → `nfc_task` notify;
  provide the RFAL platform macros (critical-section, delays, IRQ enable/disable).
- `nfc.{c,h}` wrapper + `nfc_task` worker: `rfalNfcInitialize()` (proves SPI+IRQ+rail — the first real
  milestone), then `rfalNfcDiscover(techs = NFC-A)` → **read the discovered device UID**.
- Wire **`nfc.read`** → worker runs discovery; posts UID + type to a live label. Lazy init on first
  NFC-screen entry, **safe-mode gated**, shares the SD lock.
- **Verify (incremental):** (1) `rfalNfcInitialize` succeeds / chip found; (2) read a known NTAG and a
  MIFARE Classic UID on-device.

### P2 — Tag read/write · **MEDIUM**
- **NTAG / Ultralight (T2T):** READ 0x30 / FAST_READ 0x3A / WRITE 0xA2; GET_VERSION, READ_SIG for
  NTAG21x; lock/OTP aware; full dump.
- **MIFARE Classic:** CRYPTO1 auth via **crapto1** over the ST25R3916 transparent/stream path
  (IC does framing/timing; keystream computed in SW, parity handled bit-level — the trickiest part
  of P2). **Known-key dictionary check** (iterate A/B keys per sector) → dump readable sectors.
- **ISO14443-B** (REQB→PUPI) and **ISO15693 / NfcV** (inventory→UID, read blocks) — also the
  iCLASS/PicoPass groundwork.
- Wire **`nfc.write`** (relabel stub → **"Write / Copy"**): block/page editor + copy-to-blank
  (authorized testing). Dumps → `/sd/nfc/`. **MIFARE dictionary** ships here (`/sd/nfc/mf_keys.dic`).
- **Verify:** R/W an NTAG215; dump a MIFARE Classic 1K on default keys; inventory an NfcV tag.

### P3 — Card emulation + NDEF · **HIGH · riskiest**
- **Listen/target mode:** configure the ST25R3916 as an ISO14443-A listener — respond to REQA/WUPA
  with a configured ATQA, answer anticollision (SEL) with the emulated UID, return SAK.
- **T2T emulation:** answer reader READ commands from an emulated page map (NDEF content).
- **NDEF:** parse/compose T2T TLV (0x03) records (URI, Text, …) → **`nfc.ndef`** (reads/writes NDEF
  on a present tag *and* supplies the emulated content). **`nfc.emulate`** plays a saved card /
  composed record.
- **De-risk ladder** (native listen-mode is the least-documented ST25R3916 path): (1) passive **UID
  emulation** a reader can see → (2) **T2T READ** responses → (3) **NDEF**. If T4T/APDU emulation
  slips, ship UID + static-NDEF and defer complex T4T to a follow-on rather than stall the milestone.

### P4 — Key recovery + import + saved-cards + extended parsers · **MEDIUM (mostly offline SW)**
Likely split **P4a / P4b** at PR time if it grows large.
- **mfkey32 / nested** (offline CRYPTO1 key recovery from captured reader-auth nonces, crapto1) →
  **`nfc.keyrec`**. Trace capture feeds off P3 listen-mode.
- **Saved-cards store** — NVS index (id, label, type, uid) + `/sd/nfc/<id>.{bin,nfc}` blobs; CRUD
  from **`nfc.saved`**. **`.nfc` (Flipper) import/export** parser.
- **Extended offline parsers (authorized testing):**
  - **EMV** contactless application-data read — PPSE / AID select, GPO, read records (offline read,
    no transaction).
  - **DESFire** — ISO14443-4 (RATS/PPS) APDU; enumerate application/file structure; AES/3DES auth
    where keys are known.
  - **iCLASS / PicoPass** — 15693-family HF; read config/app blocks per authorized testing.
- *Auto-NFC (geofenced) stays an **M6 + M8** composite — deferred to M8.*

## 4. Wording (safeguard-critical)

Device-class terms only, in **code, commits, PR text, and any subagent/Workflow prompt**:
"read tag UID", "read/write tag", "**copy to a blank tag**", "card emulation", "NDEF", "known-key
dictionary", "**offline key recovery (mfkey)**", "credential/application-data read (authorized
testing)", "trace capture / relay (authorized testing)". **Never** "clone a victim's card / attack /
weaponize / target". This plan also relabels the stub row "Write / Clone" → **"Write / Copy"** and
supersedes PLAN §4.1's "sniff / relay" with "trace capture / relay (authorized testing)". This is an
authorized security-testing tool on the operator's own credentials; charged vocabulary hard-fails
the automated cyber-safeguard and has killed subagent runs before.

## 5. Open risks / notes

- **P1 RFAL platform port** is the biggest single risk — the SPI-transceive glue must share SPI3
  with SD and hold CS across RFAL's multi-transfer sequences (manual GPIO4 CS +
  `spi_device_acquire_bus()` / SD lock). RFAL encodes the SPI mode/clock + protocol timing itself, so
  those are no longer hand-tuned — the port correctness is what to verify (`rfalNfcInitialize` OK).
- **RFAL is C++ (`.cpp`)** — the `rfal` component compiles as C++; `nfc.c` calls it through a small
  `extern "C"` shim. Watch component REQUIRES + include paths (RFAL's `rfal_config.h`/analog-config).
- **P3 listen-mode** (RFAL card-emulation) is the hardest capability item; prototype-first
  (UID → T2T → NDEF) with fallbacks as above.
- **DLDO1 enable bit** — verify against XPowersLib at P1 bring-up (3.3 V confirmed from LilyGo HAL).
- **On-device verification needs sample credentials the operator owns** — NTAG215, MIFARE Classic
  1K, an ISO15693 tag, and (for P4) a DESFire + an EMV card for authorized self-test.
- **WDT** — the UI-liveness watchdog covers the LVGL task; `nfc_task` keeps operations bounded /
  chunked so a long recovery can't starve the system.
